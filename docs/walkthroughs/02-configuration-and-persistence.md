# 02 — Configuration and persistence

> **Milestones:** M5 · **Status:** done · **Previous:** [01 — Baseline and quality gates](01-baseline-and-quality-gates.md) · **Next:** [03 — Envelope encryption](03-envelope-encryption.md)

This phase gave the API a configuration it can trust and a database it can survive. Settings come from the environment and Docker secret files and refuse to start a half-configured production. Persistence sits behind a unit-of-work seam with an in-memory implementation and a PostgreSQL one, checked against each other by a shared contract suite. Postgres runs with two roles so the app cannot change its own schema, a bounded pool that answers `503` instead of hanging, and server-side timeouts. Every response leaves through middleware that adds security headers and a request id, and every error is a problem document that never echoes what the user sent. It implements [`architecture.md` §5.3](../architecture.md#53-request-integrity) (headers, errors, logs) and rules 7 and 9 of [§5.7](../architecture.md#57-concurrency-and-resources).

## What this phase delivers

- **`Settings`** (`app/settings.py`): `HUMANI_T_*` environment variables and, when `/run/secrets` exists, Docker secret files; production refuses to start without its backends and an `https://` origin; a database without encryption keys is refused everywhere.
- **The composition root** `build_providers(settings)` and `Providers.close()`, used by the app's lifespan and by every CLI command.
- **The storage seam** (`app/storage/base.py`): `StorageProvider.unit_of_work()` yielding a `UnitOfWork` with repositories; `MemoryStorage` and `PostgresStorage` implement it.
- **PostgreSQL** with SQLAlchemy Core, asyncpg and Alembic; migrations `0001`–`0004`; two roles (`humani_t_migrator`, `humani_t_app`); two databases (`humani_t`, `humani_t_test`).
- **A bounded pool** (10 connections, no overflow, 5-second wait, then `503`) with `pool_pre_ping`, 30-minute recycling, and Postgres-side statement (15 s) and idle-in-transaction (30 s) timeouts.
- **Middleware**: request id, security headers, a 1 MiB body limit, and the cross-site request check (its CSRF role is explained in [05](05-accounts-and-sessions.md#d512-cross-site-request-forgery-three-independent-layers)).
- **Problem responses** (RFC 9457) for every error, and **structured, redacted logs** with structlog.
- **Endpoints:** `GET /api/v1/ready` (readiness, checks the database). `GET /api/v1/info`, `/docs`, `/redoc` and `/openapi.json` exist only outside production.

## Architecture choices and why

### D2.1 The composition root builds every provider, and closes them

- **Decision:** `build_providers(settings)` in `app/api/dependencies.py` turns configuration into implementations — `MemoryStorage` or `PostgresStorage`, `MemoryRateLimiter` or `ValkeyRateLimiter`, `RecordingEmailProvider` or `SmtpEmailProvider`, `LocalKeyProvider`, `Argon2PasswordHasher`, `FakePaperSearchProvider` — and returns a frozen `Providers`. `create_app(settings, providers=…)` builds them eagerly (engines connect lazily, so tests that never start the app still get a fully wired one); the lifespan calls `providers.close()` at shutdown, and every CLI command closes them in a `finally`. Keyword arguments (`clock`, `password_hasher`, `storage`, `email`) exist only so tests can inject a movable clock, a cheap hasher and instrumented fakes.
- **Why:** one file decides every implementation (the operational form of [D1.5](01-baseline-and-quality-gates.md#d15-one-composition-root-and-an-app-factory)); and everything opened is closed, so pools and clients do not leak across reloads or CLI runs (rule 9 of [§5.7](../architecture.md#57-concurrency-and-resources)).
- **Rejected:** module-level singletons; building providers inside the lifespan (tests without a lifespan would get nothing).
- **Costs:** `build_providers` grows as seams are added.
- **Proven by:** `tests/test_concurrency_and_resources.py::TestResourceCleanup`.

### D2.2 Configuration and secrets fail closed

- **Decision:** `Settings` (pydantic-settings) reads `HUMANI_T_*` environment variables and, when `/run/secrets` is a directory, Docker secret files. Unknown fields passed to it are refused (`extra="forbid"`), the object is frozen, and secrets are `SecretStr` (masked in `repr`). Two validators run in every environment: a `database_url` without `key_encryption_keys` is refused, and production refuses to start unless `database_url`, `key_encryption_keys`, `valkey_url` and `smtp_host` are set and `public_origin` starts with `https://`. Settings never read `.env` themselves; development loads it explicitly with `uv run --env-file .env`. Only the composition root (`main.py`, `api/dependencies.py`, `cli.py`, `migrations/env.py`) imports `Settings`; lower layers receive plain values.
- **Why:** fail closed — a misconfigured production must not start "mostly working" with in-memory storage, per-process keys, per-worker rate limits or mail kept in memory. Docker secrets keep passwords out of environment variables, which leak into process listings and crash reports. Explicit `.env` loading means the test suite can never pick up a developer's database by accident. The KEK rule exists because without a configured KEK the app generates one per process: with a database, everything encrypted would be unreadable after a restart.
- **Rejected:** `.env` auto-loading; secrets in Compose `environment:` blocks; defaults that silently work in production.
- **Costs:** one more flag in development commands.
- **Unknown names are refused (closed gap):** `extra="forbid"` covers keyword and dictionary input only, because pydantic-settings looks up just the variables it knows. An extra settings source, `_UnknownNamesRefused`, runs first and refuses any `HUMANI_T_` environment variable or secret file that names no setting, so `HUMANI_T_ENVIROMENT=production` stops the process instead of starting it in development ([T2.10](#t210-a-misspelt-setting-is-refused)). The message names the key and never its value, which may be a secret.
- **Errors never print secrets (closed gap):** a failing validator used to report its whole input, which held `HUMANI_T_DATABASE_URL` with its password, and uvicorn and the CLI print that error at startup. `hide_input_in_errors=True` removes the input from every settings error ([T2.18](#t218-a-refused-configuration-never-prints-a-password)).
- **Proven by:** `tests/test_settings.py::TestProductionRequirements`, `TestAnyEnvironment`, `TestUnknownSettings`, `TestSecretsNeverAppearInErrors` (raised, through the CLI and through uvicorn's import of `app.main`), `test_env_example_documents_every_setting`.

### D2.3 Pydantic only at the two boundaries

- **Decision:** Pydantic appears in exactly two places, both reading untrusted input: `app/api/schemas/` (HTTP) and `app/settings.py` (the environment). The domain uses frozen dataclasses that validate themselves. HTTP JSON is validated into a schema, then converted with `to_domain()`; responses are built with `from_domain()`. The account schemas set `extra="forbid"`, so an unexpected field (a `role` or `is_admin` smuggled into a sign-in) is a `422`, not silently dropped.
- **Why:** Pydantic checks **shape** ("is this an email address?"); the domain checks **meaning** ("is this password acceptable for this user?"). Keeping Pydantic out of the domain means the wire format and the deployment's configuration never leak into the rules, and a domain `ValueError` becomes a `422` only at the boundary.
- **Rejected:** Pydantic models as domain entities (couples rules to the HTTP format).
- **Costs:** a conversion step at the boundary.
- **Proven by:** the import-linter contracts (domain and application may not import `pydantic`); [T2.11](#t211-unexpected-fields-are-refused-at-the-boundary).

### D2.4 A unit of work with repositories

- **Decision:** persistence is exposed as repositories (`data_keys`, `audit`, `users`, `sessions`, `invitations`, `password_resets`) on a `UnitOfWork`, which is one transaction: nothing is visible to others until `commit()`, and leaving the `async with storage.unit_of_work()` block without committing rolls back. `unit_of_work()` raises `StorageUnavailableError` when no connection is available in time. Use cases open their own short units of work; the shape they follow (short read → slow work with no connection held → short race-safe write → side effects after commit) is explained in [D5.14](05-accounts-and-sessions.md#d514-rules-for-concurrency-and-resources).
- **Why:** this is the Unit of Work pattern from *Architecture Patterns with Python* (chapter 6). Owning transactions inside the use case, rather than one per HTTP request, is what makes it possible to release the database connection while Argon2 runs, which keeps a burst of sign-ins from exhausting the pool. Encryption and audit write *inside the caller's* unit of work, so an action and its key or audit record commit or roll back together.
- **Rejected:** a transaction per HTTP request (holds a connection for the whole request, including hashing and email); an implicit session object passed everywhere.
- **Costs:** a use case has more steps, and a second transaction must re-check anything that could have changed since the first.
- **Where:** [`app/storage/base.py`](../../services/api/app/storage/base.py) — note the comment above `UserRepository`: writes another request could race with are conditional or version-checked, never blind.

### D2.5 SQLAlchemy Core, not the ORM

- **Decision:** tables are declared with SQLAlchemy Core (`storage/postgres/tables.py`); repositories build SQL with Core expressions and map rows to domain dataclasses by hand (`_RecordTable` does it generically for types whose fields match their columns).
- **Why:** the domain types are frozen dataclasses; the ORM wants mutable, instrumented classes and would pull SQLAlchemy into the domain. Core keeps SQL explicit, which matters for the conditional updates (`UPDATE … WHERE revoked_at IS NULL`, `WHERE version = :v`) that make writes race-safe. Core expressions are parameterised, so they cannot be injected.
- **Rejected:** the ORM; raw SQL strings (no composition, easy to make injection mistakes).
- **Costs:** more mapping code than the ORM would need.

### D2.6 Two database roles, migrations and a separate test database

- **Decision:** `humani_t_migrator` owns the schema and is used only by Alembic (`migrations/env.py` reads only `HUMANI_T_MIGRATION_DATABASE_URL`). `humani_t_app` can read and write rows but cannot create, alter or drop anything, and cannot update or delete audit events. Migrations in `services/api/migrations/versions/` are written by hand and are the source of truth for the schema; `tables.py` must match them. Contract tests use a separate database, `humani_t_test`. The app never creates tables at start-up.
- **Why:** if the API process is compromised, the attacker cannot change the schema or rewrite history. Tests delete what they write, so they must never point at development data (they once did, during the checkpoint work, and wiped the development accounts). Hand-written migrations are reviewed like code; autogenerated ones hide surprises.
- **Rejected:** one superuser for everything; `metadata.create_all()` at app start-up.
- **Costs:** two connection strings and a migration step; the test database must be migrated too ([S0.6](00-setup.md#s06-migrate-the-test-database)).
- **Proven by:** `tests/test_storage_contract.py::TestPostgresAuditGuarantees::test_the_app_role_cannot_rewrite_history`; [T2.12](#t212-the-app-role-cannot-change-the-schema).

### D2.7 A bounded pool that fails fast, and server-side timeouts

- **Decision:** `PostgresStorage.from_url` builds an async engine with `pool_size` 10, `max_overflow=0`, `pool_timeout` 5 seconds, `pool_pre_ping=True` and `pool_recycle=1800`. If no connection is free in time — or the database is unreachable — `unit_of_work()` raises `StorageUnavailableError`, answered `503` with `Retry-After: 5`. Each connection sets `statement_timeout` (15 s) and `idle_in_transaction_session_timeout` (30 s) through asyncpg's `server_settings`.
- **Why:** the database sees a predictable number of connections; overload is reported, not queued forever; a bug that leaves a transaction open cannot hold locks indefinitely. Pre-ping drops connections Postgres closed while idle, so the first request after a database restart succeeds instead of failing.
- **Rejected:** overflow connections (unbounded under a burst); long or infinite pool waits (requests pile up and every client times out together).
- **Costs:** under a real burst, some requests get `503` and must retry.
- **Proven by:** `tests/test_storage_contract.py::TestPostgresConcurrency::test_the_pool_is_bounded_and_fails_fast`, `test_stuck_statements_and_idle_transactions_time_out`; `tests/test_concurrency_and_resources.py::TestOverloadIsReportedNotCrashed::test_an_unavailable_database_answers_503_with_retry_after`.

### D2.8 In-memory storage plus contract tests

- **Decision:** `MemoryStorage` implements every repository for fast tests and for running without a database. Its transactions are real: changes are staged on a copy and only replace the shared state on `commit`, so a test that forgets to commit fails as it would against Postgres. Contract suites (`tests/test_storage_contract.py`, and `tests/test_ratelimit_contract.py` in phase 05) run the **same** tests against memory and, when `TEST_DATABASE_URL` / `TEST_VALKEY_URL` are set, against real Postgres and Valkey.
- **Why:** fast tests most of the time, and proof that the fake behaves like the real thing.
- **Limit to know:** the in-memory storage is not truly concurrent (last commit wins). Concurrency guarantees are proven by the **Postgres** runs, not the memory ones.

### D2.9 Middleware as plain ASGI, in a deliberate order

- **Decision:** six middleware classes, written as plain ASGI rather than Starlette's `BaseHTTPMiddleware` (which buffers streaming responses and would break the SSE endpoints planned in phase 08). Starlette runs the last-added first, so for every request:
  1. **`ClientAddressMiddleware`** settles the client address: the connecting peer, or the address a trusted proxy names in `X-Forwarded-For` ([05](05-accounts-and-sessions.md) D5.6).
  2. **`RequestIdMiddleware`** gives the request an id (or keeps a safe one from the proxy), binds it to every log line written while the request is handled, and echoes it in `x-request-id`.
  3. **`SecurityHeadersMiddleware`** wraps the response, so whatever happens below it leaves with the security headers.
  4. **`UnhandledErrorMiddleware`** turns an exception that no handler took into the `500` problem document, inside the headers and the request id, and logs `unhandled_error` with the request id bound.
  5. **`BodySizeLimitMiddleware`** refuses bodies over 1 MiB with `413` before reading them.
  6. **`CrossSiteRequestMiddleware`** refuses a state-changing request with `403` if `Origin` or `Sec-Fetch-Site` show it came from another site, and with `415` if its body is not JSON.
  7. Then FastAPI routing, Pydantic validation, the route, and the error handlers.
- **Why:** the request id is bound before anything can log, and security headers wrap even the refusals that answer without reaching a route. The `500` is produced inside both decorating middleware, and outside the two that only refuse, so a `413` from the body limit is never mistaken for a crash.
- **Rejected:** converting the exception in `RequestIdMiddleware`: the `500` would get the id but not the security headers, which are added further in.
- **Where:** [`app/main.py`](../../services/api/app/main.py) `_install`, [`app/api/middleware.py`](../../services/api/app/api/middleware.py).

### D2.10 Security headers

- **Decision:** every response carries `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; base-uri 'none'; form-action 'none'`, `Strict-Transport-Security: max-age=63072000; includeSubDomains`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`, and `Cache-Control: no-store`. The development-only docs paths (`/docs`, `/docs/oauth2-redirect`, `/redoc`, `/openapi.json`) are exempt from the CSP **and** from `Cache-Control: no-store`, because Swagger UI loads its scripts from a CDN; they keep every other header. Headers a route sets itself are not overwritten (`setdefault`).
- **Why:** API responses are data, never documents: nothing in them should load, frame or run. `no-store` keeps project data out of browser and proxy caches.
- **Rejected:** relying on the reverse proxy alone (the app may be reached directly).
- **Costs:** none for JSON; the web app's own, stricter CSP with Trusted Types ([`architecture.md` §5.3](../architecture.md#53-request-integrity)) arrives with Caddy in M13.
- **Proven by:** `tests/test_http_hardening.py::TestSecurityHeaders`.

### D2.11 Errors as problem documents

- **Decision:** every error is an RFC 9457 `application/problem+json` document: `type` (`about:blank`), `title` (the HTTP reason phrase), `status`, usually `detail`, and sometimes extensions. Validation errors (`422`, `"The request body is not valid."`) list `loc`, `msg` and `type` for each problem but never the submitted value. Unexpected errors say only `"An unexpected error occurred. Quote the request id when reporting it."`. Domain errors map to status codes in one place:

| Error | Status |
| --- | --- |
| `InvalidCredentialsError`, `ReauthenticationRequiredError` (adds `"reauthentication_required": true`), no or dead session (`"Sign in to continue."`) | 401 |
| `CurrentPasswordIncorrectError`, `ForbiddenError`, missing or wrong CSRF token, cross-site request | 403 |
| `NotFoundError`, unknown path | 404 |
| `InvalidTokenError` | 400 |
| `EmailTakenError`, `ConcurrentUpdateError` | 409 |
| Body too large / not JSON | 413 / 415 |
| `PasswordRejectedError` (adds `violations`), request validation, a domain `ValueError` on the search routes | 422 |
| `ThrottledError` (adds `Retry-After`) | 429 |
| `EmailDeliveryError` (only invitations raise it to the caller) | 502 |
| `PaperSourceUnavailableError` (adds `source_id`), `InferenceUnavailableError`: a plain message, no host, address or upstream error text; the reason goes to the log | 502 |
| `StorageUnavailableError` (adds `Retry-After: 5`) | 503 |
| anything else | 500 |

- **Why:** one shape for clients to handle, and one place deciding what an error may reveal. Echoing input could reflect the very personal data the user was trying to send. Error *messages* in the domain are written to be safe to show.
- **Where:** [`app/api/errors.py`](../../services/api/app/api/errors.py); the account errors are introduced in [05](05-accounts-and-sessions.md).
- **A `500` is decorated like any other response (closed gap):** Starlette installs a catch-all handler in its outermost error middleware, outside the custom middleware, so a `500` used to leave without the security headers or `x-request-id`, and its log line without `request_id`. `UnhandledErrorMiddleware` (D2.9) now answers it inside them; the catch-all handler remains only for a failure in the outermost middleware ([T2.19](#t219-an-unexpected-error-carries-the-headers-and-the-request-id)).
- **Proven by:** `tests/test_http_hardening.py::TestProblemResponses`, `TestUnexpectedErrors`, `TestUnavailableUpstreams`.

### D2.12 Request ids and structured, redacted logs

- **Decision:** structlog writes JSON in production and readable lines in development, with an ISO UTC timestamp and level, plus the request id on every line written while a request is being handled (bound with contextvars by `RequestIdMiddleware`). An incoming `x-request-id` is kept only if it matches `^[A-Za-z0-9-]{8,64}$`; anything else is replaced by a random 32-hex id, so a proxy header cannot smuggle a fake log entry. A processor replaces the value of any top-level field whose name matches `pass(word)?|secret|token|cookie|authorization|api[_-]?key|email|session|otp|recovery` with `[REDACTED]`.
- **Why:** logs are often shipped to third parties and kept long; redaction in the pipeline catches careless logging at call sites. A request id ties a user's report to the log lines.
- **Rejected:** the standard `logging` module with a JSON formatter (no processor pipeline for redaction); loguru.
- **Costs:** another logging layer beside uvicorn's own access log, which is standard `logging`, prints one line per request, and carries no request id.
- **Limits:** redaction looks at top-level field names only (a nested `{"token": …}` passes through) and never at the event message itself (gap G5). The application logs only warnings and errors today, so most requests produce only uvicorn's access line.
- **Where:** [`app/observability.py`](../../services/api/app/observability.py).
- **Proven by:** `tests/test_http_hardening.py::TestRequestId`, `TestUnexpectedErrors::test_the_error_is_logged_with_the_same_request_id`, `tests/test_observability.py::TestRedaction`, and [T2.16](#t216-log-redaction).

### D2.13 Bounded request bodies

- **Decision:** bodies over 1 MiB are refused with `413` (`"The request body is too large."`) — immediately if `Content-Length` says so, or as soon as a streamed (chunked) body passes the limit.
- **Why:** one huge request must not be read entirely into memory. Caddy will enforce a limit too (M4); this one holds if the app is ever reached directly. Uploads will get their own, larger route.
- **Proven by:** `tests/test_concurrency_and_resources.py::TestOverloadIsReportedNotCrashed::test_an_oversized_request_body_is_refused_before_it_is_read`.

### D2.14 Liveness and readiness are different questions

- **Decision:** `GET /health` answers "is this process up" and touches nothing; `GET /ready` answers "can it serve" by running `SELECT 1` (`StorageProvider.is_ready()`), returning `503` (`"The database is not reachable."`) when it cannot.
- **Why:** conflating the two makes deploys hard to debug: a failing dependency looks like a dead process, and an orchestrator restarts a healthy process for a database outage.
- **Proven by:** `tests/test_http_hardening.py::TestReadiness`, `tests/test_health.py`.

### D2.15 Introspection only outside production

- **Decision:** `/docs`, `/redoc`, `/openapi.json` and `/api/v1/info` exist only when `ENVIRONMENT` is not `production`.
- **Why:** Swagger UI loads scripts from a CDN, which a strict CSP forbids; and `/info` and the schema advertise every route and implementation to anyone who asks — useful to a developer and an attacker alike.
- **Costs:** production clients get the OpenAPI document from the repository (committed in M13), not from the server.
- **Proven by:** `tests/test_http_hardening.py::TestProductionSurface`.

| Not used | Why not |

## Libraries

### pydantic-settings 2.16.1

- **What it does:** builds a settings object from environment variables and secret files, with Pydantic's validation and cross-field validators.
- **Why this one:** typed, validated configuration with Docker secret support (`secrets_dir`) and model validators for the production rules.
- **Alternatives:** python-decouple, dynaconf, plain `os.environ`.
- **Trade-offs:** another Pydantic dependency; its `.env` behaviour needs care (we load `.env` explicitly instead); unknown environment variables are ignored unless a source refuses them, which ours does (D2.2); validation errors repeat their input unless `hide_input_in_errors` is set, which ours does.

### SQLAlchemy 2.1.6 (`sqlalchemy[asyncio]`, with greenlet 3.5.6)

- **What it does:** the database toolkit. We use its **Core** layer to declare tables and build SQL with Python expressions, its async engine, and its connection pool.
- **Why this one:** mature, explicit SQL construction that cannot be injected; a well-tested pool with pre-ping, recycling, timeouts and a hard size.
- **Alternatives:** the SQLAlchemy ORM (D2.5); SQLModel (ORM-centric); raw asyncpg (no composition, more error-prone).
- **Trade-offs:** large, with a learning curve; the asyncio extension runs on greenlet under the hood.
- **What we gave up:** the ORM's automatic change tracking and relationship loading.

### asyncpg 0.32.0

- **What it does:** the PostgreSQL driver: speaks the Postgres wire protocol directly, asynchronously.
- **Why this one:** the fastest Python Postgres driver; lets us set server-side settings (statement and idle timeouts) per connection through `server_settings`.
- **Alternatives:** psycopg 3 (also async, closer to the DB-API standard).
- **Trade-offs:** Postgres-only (fine: Postgres is the only target); not DB-API compliant, so SQLAlchemy adapts it.

### Alembic 1.20.1

- **What it does:** database migrations: versioned scripts that move the schema forward (and back), recorded in `alembic_version`. Here it runs asynchronously as the schema owner (`migrations/env.py`), and `alembic.ini` holds no credentials.
- **Why this one:** the standard companion to SQLAlchemy.
- **Trade-offs:** autogenerated migrations need review; we write them by hand and keep `tables.py` in step.

### structlog 26.1.0

- **What it does:** structured logging: log lines are key–value events passed through a pipeline of processors (contextvars, level, timestamp, redaction, exception formatting) and rendered as JSON or text.
- **Why this one:** machine-readable logs and a single place to redact secrets.
- **Alternatives:** the standard `logging` module with a JSON formatter; loguru.
- **Trade-offs:** another logging layer to learn alongside the standard library's (which uvicorn still uses for its access log).

### PostgreSQL 18 (`postgres:18-alpine`)

- **What it does:** the relational database for users, sessions, tokens, wrapped keys and the audit log.
- **Why this one:** transactional, mature, row-level locking (which the atomic claims rely on), roles and grants, triggers, check constraints, and server-side timeouts.
- **Alternatives:** MySQL (weaker on some of these features); SQLite (no concurrent writers, no roles — fine for a desktop app, wrong for a server).
- **Trade-offs:** an operational service to back up and patch.

### T2.14 A database outage is reported, not crashed

- **Do:** from `services\api`: `docker compose -f ..\..\compose.dev.yaml stop postgres`. Then `POST {{base}}/auth/login` (admin credentials), `GET {{base}}/ready` and `GET {{base}}/health`. ## Glossary

| Term | Meaning |
| --- | --- |
| **ASGI middleware** | A wrapper around the app that sees every request and response; plain ASGI does not buffer streams. |
| **Contract test** | The same test suite run against a fake and the real implementation, proving they behave alike. |
| **CSP** | Content Security Policy: a header telling browsers what a response may load or run. |
| **HSTS** | Strict-Transport-Security: tells browsers to use HTTPS only for this host; ignored over plain HTTP, so it matters from M4. |
| **Fail closed** | When something is missing or wrong, refuse to run rather than run with weaker defaults. |
| **Liveness / readiness** | "Is the process up?" / "Can it serve requests now?" |
| **Optimistic locking** | Saving only if the record's version is unchanged since it was read; otherwise refusing. |
| **Pool pre-ping** | Testing a pooled connection before handing it out, so a dead one is replaced. |
| **Problem document** | The RFC 9457 JSON format for HTTP errors. |
| **Request id** | A per-request identifier echoed in `x-request-id` and bound to log lines. |
| **Schema owner** | The role that owns the tables and may change them (`humani_t_migrator`). |
| **Statement timeout** | A Postgres setting that cancels any statement running longer than a limit. |
| **Unit of Work** | One transaction, exposing repositories; nothing is visible to others until commit. |
