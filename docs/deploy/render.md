# Hosting on Render

This guide lives only on the `onrender-production` branch. That branch is `staging` plus the files Render needs, and changes flow one way: `staging` → `onrender-production`, never back.

## What Render runs

[`render.yaml`](../../render.yaml) is a Render *Blueprint*: a list of what Render should create. Render reads it and creates three things in Frankfurt:

| Name | What it is | Why |
| --- | --- | --- |
| `humani-t` | A web service built from [`infrastructure/render/Dockerfile`](../../infrastructure/render/Dockerfile) | Runs Caddy (the web page and security headers), the API and the worker in one container, with a 1 GB disk for uploaded files |
| `humani-t-db` | Render Postgres, smallest paid plan | The database. The free plan deletes itself after 30 days |
| `humani-t-kv` | Render Key Value, free plan | Rate limits and wake-up signals; losing it on a restart loses no data |

The API and the worker share one container because Render attaches a disk to one service only, and both read the uploaded files.

The service is on a paid plan, so it never goes to sleep and needs no cron job to keep it awake. Only free web services sleep after 15 minutes without visitors.

Prices change; see [render.com/pricing](https://render.com/pricing) for the web service (`standard`), Postgres (`basic-256mb`) and Key Value (`free`) plans.

## Before you start

You need four things ready to paste:

1. **An OpenAI API key.** At [platform.openai.com](https://platform.openai.com), open *API keys*, create one, and copy it. It starts with `sk-`. Set a monthly spending limit under *Limits* while you are there.
2. **An OpenAI model name.** Pick a current model from OpenAI's *Models* page that supports structured outputs, for example a small, inexpensive one. You type its name exactly, such as the ID shown on that page.
3. **An email account for sending mail.** Sign-in links and invitations go out by email, so the app needs an SMTP service: any transactional email provider works. From it you need the *SMTP host* (a server name such as `smtp.example.com`), a *username*, a *password*, and a *sender address* on a domain you have verified with that provider.
4. **A key-encryption key.** This key protects everything in the database. Make one on your computer:

   ```powershell
   Set-Location C:\Users\fiifidawson\devdawson\GitHub\humani-t\services\api
   uv run python -m app.cli generate-kek
   ```

   The value you paste into Render is `1:` followed by what that prints, for example `1:q3J…=`. **Save it in your password manager.** If it is lost, nothing in the database can ever be read again.

## Create the services

1. Sign in at [dashboard.render.com](https://dashboard.render.com). Connect your GitHub account if Render asks, and allow it to see the `humani-t` repository.
2. Click **New** → **Blueprint**.
3. Choose the `humani-t` repository and the branch **`onrender-production`**. Render finds `render.yaml` and lists the three resources.
4. Render asks for each value marked `sync: false`. Paste them in:

| Field | What to enter |
| --- | --- |
| `HUMANI_T_KEY_ENCRYPTION_KEYS` | `1:` and your key from step 4 above |
| `HUMANI_T_INFERENCE_MODEL` | The OpenAI model name |
| `HUMANI_T_INFERENCE_TOKEN` | Your OpenAI API key |
| `HUMANI_T_OPENALEX_MAILTO` | An email address OpenAlex may contact about heavy use; it gives faster searches. Leave empty if you prefer |
| `HUMANI_T_SMTP_HOST` | Your email provider's SMTP host |
| `HUMANI_T_SMTP_USERNAME` | Its SMTP username |
| `HUMANI_T_SMTP_PASSWORD` | Its SMTP password |
| `HUMANI_T_SMTP_SENDER` | The sender, written `humani-t <no-reply@your-domain>` |

5. Click **Apply**. Render creates the database and the Key Value store, builds the image (about 10 minutes the first time), runs the pre-deploy step, and starts the service.

Everything else is already set in `render.yaml`. The values worth knowing about:

| Setting | Value | Meaning |
| --- | --- | --- |
| `HUMANI_T_ALLOW_HOSTED_INFERENCE` | `true` | The model is OpenAI's, outside the deployment. Text is masked before it is sent |
| `HUMANI_T_ALLOW_UNMASKED_HOSTED_INFERENCE` | `false` | Project owners cannot turn masking off |
| `HUMANI_T_MALWARE_SCANNER` | `none` | No virus scanner runs on Render; each document says it was not scanned |
| `HUMANI_T_PAPER_SOURCES` | `openalex,europepmc,arxiv` | Where Discover searches |
| `DB_APP_PASSWORD`, `DB_MIGRATOR_PASSWORD` | generated by Render | Passwords for the app's two database users, below |

## The two database users

As with Docker Compose, the app uses two database users. `humani_t_migrator` owns the tables and only runs migrations. `humani_t_app` reads and writes rows and cannot change the audit log. Render gives you one user, so the pre-deploy step ([`create_roles.py`](../../infrastructure/render/create_roles.py)) makes the other two with it before every deploy.

If the first deploy fails with *"The Render database user may not create roles"*, open the `humani-t` service → **Environment**, set `DB_SEPARATE_ROLES` to `false`, and deploy again. The app then runs as Render's user. It still works, but a fault in the app could alter tables that are otherwise append-only.

## Create your administrator

1. Open the `humani-t` service → **Shell**.
2. Run this, with your own email address:

   ```bash
   humani-t-cli create-admin --email you@example.org --password-stdin
   ```

3. Type a password of at least 15 characters, press **Enter**, then **Ctrl+D**. Typing it this way keeps it out of the shell's history.
4. Open the service's address, shown at the top of its page as `https://humani-t-….onrender.com`, and sign in. You will be asked to set up a passkey or an authenticator app.

Then invite everyday accounts from the app, as described in the self-hosting guide.

## Updating the hosted copy

Merge `staging` into the branch and push. Render rebuilds and redeploys on its own:

```powershell
Set-Location C:\Users\fiifidawson\devdawson\GitHub\humani-t
git switch onrender-production
git pull
git merge staging
git push
```

Each deploy has a short interruption: a service with a disk stops the old copy before starting the new one.

## Your own domain

Add the domain under the service's **Settings** → **Custom Domains** and follow Render's DNS steps. Then add an environment variable `PUBLIC_ORIGIN` set to `https://your-domain` so that sign-in cookies, links in emails and link previews use it.

## Limits to know

- **No virus scanning.** ClamAV needs more memory than this plan has.
- **One instance.** A service with a disk cannot be scaled to more than one.
- **Data location.** Everything is stored in Render's Frankfurt region. Text sent to OpenAI is masked first.
- **Backups.** Check which backups your Postgres plan keeps on the database's page in the dashboard, and how Render snapshots the disk on the service's **Disks** page.

## Taking it down

Delete the Blueprint's three resources in the Render dashboard; deleting the database deletes its data. Then delete the `onrender-production` branch.
